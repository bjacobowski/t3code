01 — START

Executive summary

The shortest useful explanation: T3 Code is not an editor with agents embedded in each client. It is a server-owned agent runtime with several control surfaces.

The invariant

The server is the execution boundary.

Provider subprocesses, terminals, Git, checkpoints, filesystem reads, settings, and durable state all live on the machine running t3. Web, desktop renderer, and mobile are clients of that environment.

The center of gravity

Typed commands become persisted events.

The orchestration engine serializes commands, a pure decider emits domain events, SQLite stores them, projectors derive read models, and reactors perform asynchronous side effects.

Remote-ready

Direct, bearer-paired, relay, Tailscale, and desktop-managed SSH connections all terminate at the same server protocol.

Multi-surface

Web and mobile share nonvisual runtime logic. Desktop wraps the web app and adds an Electron main process, local backend supervision, IPC, WSL, and SSH.

Performance posture

Scoped subscriptions, cached projections, bounded histories, native telemetry, and avoiding unnecessary reconnects or process polling are deliberate themes.

Start here: read docs/internals/overview.md, then docs/internals/glossary.md. The code becomes much easier once “environment / project / thread / turn / event / reactor / checkpoint” are precise.
02 — MODEL

The mental model

Four boundaries explain most of the repository. Keep them separate and the system is surprisingly navigable.

EnvironmentOne running T3 server plus the machine, providers, credentials, state, and workspaces it owns. Stable identity is persisted under the server state directory.
ProjectAn environment-local workspace record rooted at a directory. A logical repository may have separate projects in separate environments.
ThreadThe durable conversation and workspace-history unit. It owns messages, activities, session state, turns, and checkpoint summaries.
TurnOne user-to-agent cycle. It ends when provider session status leaves running; checkpoint/diff follow-up can settle later.

Intent versus fact

Commands request a state transition. Events state that something happened. The decider is the policy boundary between them; the projector turns facts into the UI-shaped read model.

Core versus edges

Orchestration is provider-neutral and mostly pure. Complexity is pushed to adapters: CLI protocols, OS APIs, Electron IPC, persistence, remote auth, and networking.

04 — TRACE

A turn, end to end

Trace this path whenever behavior is confusing. It crosses every intentional boundary in the architecture.

01 / UIUser submits a message from web or mobile UI through domain Atom operations.
02 / RPCShared runtime resolves the current environment session and invokes a typed orchestration RPC.
03 / ENGINEThe command enters a single queue; durable receipt lookup makes retries idempotent.
04 / DECIDEPure domain logic validates invariants and emits one or more events.
05 / COMMITEvent append, SQL projection, in-memory projection, and receipt happen transactionally.
06 / REACTProvider and checkpoint reactors observe committed intent and perform side effects.
07 / STREAMProvider output is normalized into internal commands; clients receive updated thread projections.

Detailed sequence

  • thread.turn.start is dispatched with a command ID.
  • OrchestrationEngine.ts totally orders it with all other commands.
  • decider.ts emits durable intent events.
  • ProviderCommandReactor.ts calls ProviderService, which routes by thread/provider instance.
  • The adapter talks to a CLI subprocess and emits provider-runtime events.
  • ProviderRuntimeIngestion.ts turns those into internal orchestration commands.
  • Assistant text, tool activity, approvals, and session state are projected and streamed.
  • A transition out of running settles the turn; checkpoint capture and diff finalization follow.

Why this indirection exists

The persisted domain history is stable even though provider protocols are not. A provider crash, reconnect, client retry, or delayed checkpoint is handled at an edge without turning the UI into the source of truth.

The cost is more concepts and more “requested → completed” pairs. Search for both the command/event name and its reactor when tracing behavior.

05 — CORE

Server internals

apps/server is both the published t3 CLI and the execution runtime. It owns everything with machine authority.

Transport boundary

apps/server/src/ws.ts serves the Effect RPC group. Upgrade authentication happens before RPC, then RpcAuthorization.ts checks scopes per method. Streaming subscriptions replace a global broadcast bus.

Composition

Effect Layers assemble services and explicit dependencies. Startup has a command-readiness gate: reactors/settings/keybindings become ready before the HTTP listener is marked ready, so any accepted socket can dispatch safely.

Engine

A single worker fiber serializes commands. Accepted command receipts make retry safe; failures reconcile persisted events beyond the starting sequence.

Decider

Pure command + current state → events. Invariants such as project/thread existence and archival state are centralized here and in commandInvariants.ts.

Projectors

The pure in-memory projector and persisted projection pipeline build read-optimized state. Retention is bounded for large thread collections.

Reactors

Queue-backed workers handle provider calls, provider output ingestion, checkpoints, and reverts after events commit.

Persistence

SQLite stores append-only events, durable receipts, auth records, and denormalized projection tables. The repository currently contains 46 migration-related files.

Machine services

Terminal PTYs, filesystem, previews, MCP, source control, VCS, background service management, attachments, diagnostics, and telemetry.

dispatch(command)
  → commandQueue.take()                       // total ordering
  → receipt lookup                            // retry idempotency
  → decideOrchestrationCommand(command,state) // pure policy
  → SQL transaction {
      append(events)
      project tables
      write accepted receipt
    }
  → swap in-memory read model
  → publish committed events                  // subscriptions + reactors
Testing seam: asynchronous workers expose drain(), and test-only runtime receipts mark milestones. Production receipt publishing is intentionally a no-op; never build application behavior on it.
06 — EDGE

The provider boundary

Provider complexity is deliberately localized. Orchestration addresses threads and provider instances, not CLI-specific protocols.

Two registries

ProviderInstanceRegistry turns configured instance entries into live scoped adapters. ProviderAdapterRegistry resolves instance IDs. ProviderService adds thread/session routing above them.

One normalized contract

Adapters start/stop sessions, send/interrupt turns, respond to approvals/input, and expose normalized runtime event streams. Process scope closure owns cleanup.

Adding a common provider

Implement a driver declaration and adapter, then register it in apps/server/src/provider/builtInDrivers.ts. If the existing normalized capabilities suffice, orchestration and clients should not change. If they do not, treat that as a contract and multi-surface design change—not an adapter-only patch.

08 — LINK

Connection runtime

packages/client-runtime is the nonvisual client brain. It intentionally has no package-root export; subpaths are architectural boundaries.

RESOLVERTurns primary, bearer, relay, or SSH catalog entries into authenticated endpoints.
DRIVERPerforms one prepare/open/synchronize attempt.
RPC SESSIONOwns one socket attempt, client, initial config, probe, ready, and closed signals.
SUPERVISORThe only retry owner. Manages desired state, session scope, backoff, wakeups, and health.
REGISTRYOwns catalog and one environment-scoped supervisor per environment.

Retry semantics

Transient failure retries forever with exponential backoff capped at 16 seconds; 30 seconds of stability resets it. Offline waits do not spend retry attempts. Authentication/configuration failures block until input changes.

Foreground semantics

Activation does not blindly reconnect. While connected, the runtime probes the current lease; meaningful mobile background suspension can request replacement because the OS may have killed the socket.

Data semantics

Finite requests, durable subscriptions, and commands are separate APIs. Shell/thread snapshots remain available offline, while sync status is explicit and independent from transport status.

Platform contract

Web/mobile provide network status, application wakeups, cloud credentials, device identity, registrations, persistence, HTTP, crypto, and telemetry. They adapt capabilities—not connection policy.

09 — TRUST

Remote access & authentication

Access method and launch method are independent. Several routes can reach the same stable environment identity.

Connection targetWhat it meansWhere complexity lives
PrimaryPlatform-managed local server: CLI-served web or desktop backend.Platform registration and desktop backend pool.
BearerManually paired direct HTTP/WebSocket endpoint, including Tailscale URLs.Onboarding, endpoint selection, environment auth.
RelayT3 Connect-managed tunnel for NAT/firewall/mobile reachability.Cloud auth, DPoP, relay discovery, tunnel lifecycle.
SSHDesktop discovers/launches a remote server and forwards a local port.Electron main + packages/ssh; renderer still sees a normal environment.

Environment credentials

Pairing bootstrap credentials exchange for scoped sessions. Browser clients use an HTTP-only session cookie; non-browser clients can use bearer tokens; relay clients can use DPoP-bound one-hour tokens.

WebSocket tickets

A long-lived credential calls POST /api/auth/websocket-ticket. Only the resulting five-minute, single-purpose ticket enters the socket URL. RPC methods still enforce scopes individually.

T3 Connect

infra/relay is Cloudflare Workers + PostgreSQL/Drizzle + Clerk + Alchemy. It brokers identity, records, discovery, and managed publishing; application traffic uses the provisioned tunnel hostname rather than flowing through the relay Worker hot path.

Hosted pairing

app.t3.codes is a static client, not a proxy. Pair tokens live in URL fragments, are exchanged directly with the backend, then stripped. HTTPS browser mixed-content constraints still apply.

Scope model: orchestration:read, orchestration:operate, terminal:operate, review:write, access:read/write, and relay:read/write. A valid socket is not blanket authorization.
10 — STATE

Data, Git & machine state

Durable application state and workspace state are related but distinct: SQLite remembers the domain; Git checkpoints remember the filesystem.

SQLite domain state

Append-only orchestration events are the history. Persisted projections answer queries efficiently, and durable command receipts make network retries idempotent. Auth, settings, environment state, and supporting records live beside them.

Git checkpoints

Turns are bracketed by hidden Git refs through the VcsCheckpointOps contract. Baseline and completed snapshots enable exact turn/thread diffs and workspace restoration.

Worktrees

A thread may run in its own Git worktree. The project keeps a workspace root; thread configuration chooses main tree or isolated path.

Terminal

The server owns PTYs and exposes attach/input/resize/restart/terminate over scoped RPC streams. Clients render terminal state but never own the process.

Filesystem & preview

Reads, diffs, project scripts, attachments, review previews, and browser preview automation cross typed server boundaries.

Telemetry

A Rust sidecar samples process trees with OS APIs. Electron contributes power/app metrics over inherited file descriptors. History is bounded in memory, not persisted.

Failure isolation: the resource monitor is a supervised executable rather than a Node native addon. A monitor crash cannot corrupt the server runtime, and missing telemetry degrades to unavailable.

13 — WORK

Development, test & release

The repository optimizes for isolated worktrees, single-origin remote-safe development, and focused deterministic verification.

First run

vp i
vp run dev          # contracts + server + web watch
# open the one-time pairing URL printed by dev-runner

Node 24 is required. Bun is optional; server platform adapters select Bun when present and Node otherwise.

Dev topology

scripts/dev-runner.ts derives stable port offsets from the worktree path and scans collisions. Vite proxies /api, /ws, /oauth, and /.well-known; never bake localhost origins into the bundle.

Worktrees default to isolated <worktree>/.t3/userdata. The main checkout defaults to ~/.t3/dev.

Focused verification

vp test run <files>, targeted lint/typecheck, worker drains, and typed receipts. Avoid sleep/poll tests and repo-wide checks during ordinary changes.

CI

Format/lint + workspace typecheck + desktop build, workspace tests, macOS mobile native static analysis, and release smoke.

Desktop release

Electron Builder emits DMG, NSIS, and AppImage; signing/notarization is conditional on platform credentials.

Other releases

Server npm package via release automation/OIDC, web deployment, Expo/EAS mobile distribution, Alchemy relay deploy, native telemetry artifacts.

Test shape

Approximately 735 test files across product workspaces. Server tests emphasize SQLite/Git/worktree behavior; web uses Vitest and MSW; desktop uses Playwright Core for preview automation.

Repository scale

Roughly 2,638 tracked files in apps/packages/infra/native/scripts/docs and ~374k non-generated TypeScript/TSX lines in product/tooling scope.

15 — READ

Design observations

These are architectural readings, not refactoring requests. They identify where the design is deep, and where changes are likely to amplify.

Strong boundary: server authority

One execution boundary makes remote behavior unsurprising. Clients never need partial filesystem, terminal, or provider implementations, and access methods do not infect domain logic.

Strong boundary: shared client runtime

Connection policy is centralized while platform differences are capability adapters. The “one retry owner” rule prevents competing reconnect loops and stale-session bugs.

Strong seam: event sourcing + adapters

Pure decider/projector logic is testable without processes, while provider volatility stays behind adapter and ingestion boundaries. Durable receipts address retries explicitly.

Strong seam: drainable workers

Queue completion is observable without timing guesses. This supports deterministic integration tests for asynchronous provider/checkpoint workflows.

Hotspot: orchestration breadth

Large command/event unions, decider switches, and projection logic mean a new cross-cutting thread behavior can touch contracts, invariants, decider, projector, persisted projection, reactor, and UI. Follow an existing command end to end.

Hotspot: provider semantic mismatch

Five CLIs differ in sessions, approvals, usage, protocol errors, and rollback. Resist leaking provider-specific conditionals into orchestration; expand normalized capabilities only when the product truly needs them.

Hotspot: remote/auth matrix

Primary, bearer, relay, SSH, browser cookies, bearer and DPoP tokens, WebSocket tickets, and hosted mixed-content rules create a large state matrix. Connection and auth changes need scenario-driven tests.

Hotspot: version volatility

Effect 4 beta, TypeScript native preview, Vite+ core, Expo/React Native, and patched dependencies increase upgrade risk. Pinning is deliberate; broad dependency upgrades should be isolated.
